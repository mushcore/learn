- "OS provides the set of **system calls** that is an interface between the operating system and the user programs."

## syscall() library function (slide 18)
- man excerpt: "DESCRIPTION **syscall()** is a small library function that invokes the system call whose assembly language interface has the specified **number** with the specified arguments. **Employing syscall() is useful, for example, when invoking a system call that has no wrapper function in the C library.**" (last sentence highlighted)

```c
#include <unistd.h>
#include <sys/syscall.h>
#include <stdio.h>

#define STDIN_FILENO 0
#define BUFFER_SIZE 100

int main() {
    char buffer[BUFFER_SIZE];
    ssize_t bytesRead;

    printf("Enter your message: ");
    fflush(stdout);
    bytesRead = syscall(SYS_read, STDIN_FILENO, buffer, BUFFER_SIZE - 1);
    if (bytesRead == -1) {
        perror("Read error");
        return 1;
    }
    buffer[bytesRead] = '\0';

    return 0;
}
```

## The 11 steps of read(fd, buffer, nbytes) (slides 19-21)
- Slide 19: "*read(fd, buffer, nbytes)* — System calls are performed in a series of steps"
  - "**Steps 1,2, and 3**: pushing the parameters onto the stack in reverse order."
  - "**Step 4**: calling to the library procedure. This instruction is the normal procedure-call instruction used to call all procedures."
  - "**Step 5**: The library procedure, possibly written in assembly language, typically puts the system-call number in a place where the operating system expects it, such as a register."
  - "**Step 6**: executing a **TRAP instruction** to switch from user mode to kernel mode and start execution at a fixed address within the kernel."
  - "**Step 7**: The kernel code that starts following the TRAP examines the system-call number and then dispatches to the correct system-call handler, usually via a table of pointers to system-call handlers indexed on system-call number."
- Slide 20:
  - "**Step 8**: At that point the system-call handler runs."
  - "**Step 9**: Once it has completed its work, control may be returned to the user-space library procedure at the instruction following the TRAP instruction."
  - "**Step 10**: This procedure then returns to the user program in the usual way procedure calls return."
  - "**Step 11**: To finish the job, the user program has to clean up the stack, as it does after any procedure call."
- Slide 21 figure, caption "The 11 steps in making the system call *read(fd, buffer, nbytes)*." Memory drawn from **Address 0xFFFFFFFF** (top) to **0** (bottom), split into **User space** (upper) and **Kernel space (Operating system)** (lower, shaded).
  - User space, upper box, labelled "Library procedure read": rows (top to bottom) "Return to caller", "Trap to the kernel", "5 Put code for read in register".
  - User space, lower box, labelled "User program calling read": rows (top to bottom) "Increment SP" (with 11), "Call read", "3 Push fd", "2 Push &buffer", "1 Push nbytes".
  - Kernel space: "Dispatch" →7→ a table (horizontal lines, the handler-pointer table) →8→ "Sys call handler".
  - Arrows: **1, 2, 3** the pushes (bottom-up: nbytes, &buffer, fd); **4** from "Call read" up to the library procedure; **5** "Put code for read in register"; **6** from "Trap to the kernel" down into "Dispatch" in kernel space; **7** Dispatch → table; **8** table → Sys call handler; **9** from Sys call handler back up to the library procedure ("Return to caller"); **10** from "Return to caller" back down to the user program; **11** "Increment SP".

## fork + waitpid example: child sums 1..100 (slide 32)
```c
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main()
{
    int status;
    pid_t fork_return = fork();
    if (fork_return == 0){
        int sum = 0;
        for(int i=1; i<101; i++){
            sum += i;
            }
        printf("child done : sum = %d \n", sum);
    }
    else{
        printf("Line : %d \n", __LINE__);
        waitpid(-1, &status, 0);
    }
    printf("Line : %d , Fork return = %d \n", __LINE__, fork_return);
    return 0;
}
```
(code line numbers: 8 fork, 9 if, 14 child printf, 17 parent printf, 18 waitpid, 20 common printf)
- Output:
```
~$ ./a.out
Line : 17
child done : sum = 5050
Line : 20 , Fork return = 0
Line : 20 , Fork return = 1825
~$
```
  The parent prints line 17 then waits in `waitpid(-1, &status, 0)`; the child computes 5050, prints, then also reaches line 20 (Fork return = 0) and exits; only then does the parent continue to line 20 (Fork return = 1825, the child's PID).

```c
     if (fork( ) != 0) {                        /* fork off child process */
         /* Parent code. */
         waitpid(−1, &status, 0);               /* wait for child to exit */
     } else {
         /* Child code. */
         execve(command, parameters, 0);        /* execute command */
     }
}
```

## Blocking and non-blocking system calls (slides 52-54)
- Slide 52: "System calls are the mechanism by which programs interact with the kernel of an operating system. In the context of file I/O operations, system calls like open, read, and write play a critical role. These operations can be executed in either blocking or non-blocking modes."
- Slide 53 (Blocking): "A **blocking system call** suspends the execution of the process until the operation is completed. For example, if you are reading from a file, the program will wait (or block) until the read operation is finished. **Most I/O system calls, by default, are blocking calls.** Example: In the example below, the open call blocks the process until the file is opened, which means that the program execution is paused until the operation completes."
```c
int fd = open("file.txt", O_RDONLY);  // Blocking call
```
- Slide 54 (Non-blocking): "A **non-blocking system call** returns immediately, even if the requested operation hasn't been completed. Instead of waiting, the program continues executing other code while periodically checking if the operation has finished. Non-blocking calls are valuable in scenarios where waiting for I/O operations—such as reading from a network socket or file—would lead to inefficient resource utilization. To enable non-blocking mode, you often use the **fcntl** system call to modify the file descriptor." Example:
```c
#include <fcntl.h>

int fd = open("file.txt", O_RDONLY);
fcntl(fd, F_SETFL, O_NONBLOCK);  // Set the file descriptor to non-blocking mode
```

## Asynchronous I/O (POSIX AIO) (slides 55-57)
- Slide 55: "**POSIX Asynchronous I/O (AIO)** provides another method of non-blocking I/O where you can initiate I/O operations and have them complete asynchronously, i.e., in the background. This allows a program to perform other tasks while waiting for the operation to complete. Functions like **aio_read, aio_write, aio_error, aio_return** and **aio_fsync** enable asynchronous operations."
- Slide 56 example (green annotation "**Blocking open**" with an arrow to the `open` line):
```c
#include <aio.h>

struct aiocb cb;
int fd = open("file.txt", O_RDONLY);

cb.aio_fildes = fd;
cb.aio_buf = buffer;
cb.aio_nbytes = sizeof(buffer);
cb.aio_offset = 0;

aio_read(&cb);  // Asynchronous read call

// You can perform other tasks here while the read operation is ongoing
```
  (`buffer` is not declared in the fragment.)
- Slide 57 example (green annotation "**Non-blocking open**"):
```c
int fd = open("example.txt", O_RDONLY | O_NONBLOCK);
```
  A red arrow from `open` leads to a man-page excerpt whose first sentence is legible: "**Note that this flag has no effect for regular files and block devices;**" — the rest of the excerpt (about four lines) is deliberately scribbled out and unreadable. (So for a regular file like example.txt, O_NONBLOCK does not make the open/read non-blocking — which is why the AIO slide calls its plain open a "Blocking open" and uses aio_read for the asynchronous part.)

## Comparison (slide 58)
- "Comparison of Blocking and Non-Blocking Approaches"
- **Blocking I/O**: "Simpler code flow." "Easier to implement in cases where performance or responsiveness isn't critical." "Program execution pauses until the I/O operation is complete."
- **Non-blocking I/O**: "Prevents program from being stalled while waiting for I/O." "Requires more complex logic (e.g., checking if the operation is complete or using event loops)." "Useful for applications that need to stay responsive (like GUIs or network servers)."
