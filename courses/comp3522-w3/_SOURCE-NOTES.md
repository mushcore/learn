## Deck 1: member initialization and default arguments (Complex)
- `class Complex { private: double r, i; ...`; first pass `Complex(double rnew, double inew) { r = rnew; i = inew; }`.
- Problem: the compiler wants every member initialized; it generates a call to the default constructor for members not initialized by us: `Complex(double rnew, double inew) : r(), i() { r = rnew; i = inew; }`. For fundamental types it doesn't matter (data members of fundamental types not in the initialization list **remain uninitialized**); for class-type members "a member data item of a class type is implicitly default-constructed if it is not contained in the initialization list".
- Always use the **member initialization list**: `Complex(double rnew, double inew) : r(rnew), i(inew) { }`.
- Same identifiers allowed: names in the list outside the parentheses refer to members; inside the parentheses names follow member-function scoping (parameters hide members): `Complex(double r, double i) : r(r), i(i) { }`.
- Second constructor `Complex(double r) : r(r), i(0) { }`, default `Complex() : r(0), i(0) { }` → "Too much!" → **default arguments**: `Complex(double r = 0, double i = 0) : r(r), i(i) { }` handles `Complex c; Complex c1(5); Complex c2(5,6);`.
- Default arguments only for **trailing** arguments: `int f(int, int = 0, char * = nullptr); // OK`, `int g(int = 0, int = 0, char *); // ERROR`, `int h(int = 0, int, char * = nullptr); // ERROR`; "space between * and = is needed": `int creates_error(char *= nullptr); // ERROR` (`*=` is an operator).
- Where do default values go? **In the function prototype in the header file**: header `void f(int x = 1, int y = 2);`, source `void f(int x, int y) { … }`.
- Style note: data members MUST be initialized in the order in which they are declared in the class; the compiler may warn (`-Wreorder`); "the order of class/struct member initialization is determined by the order of member declaration and not by the order of their appearance in member initialization list."
- Shipped Complex/main.cpp: classes A and B with copy constructors that print `A copy constructed` / `B copy constructed`; `class Complex { int r, i; A a; B b; Complex(const A &a, const B &b, int r = 0, int i = 0) : a(a), b(b), r(r), i(i) { cout << "constructor of complex" << endl; } ...}`; main `A a; B b; Complex c{a,b,5,0,}; cout << c.get_r() << " " << c.get_i() << endl;` → output `A copy constructed`, `B copy constructed`, `constructor of complex`, `5 0`; g++ warns `'Complex::b' will be initialized after 'int Complex::r' [-Wreorder]` (list order a, b, r, i vs declaration order r, i, a, b; members are still initialized r, i, a, b).
- Default constructor (close analysis): a constructor with no arguments or default values for every argument; not mandatory but define one whenever possible: containers (lists, trees, matrices) of types without default constructors are cumbersome; eliminates uninitialized variables of the type; variables declared in an outer scope for algorithmic reasons must already be constructed with a meaningful value. "Ask yourself: does this type have a 'special' value or state we can 'naturally' use as a default?"
- Default member values: `double r = 0.0, i = 0.0;` in the class; then only set values in the constructor that differ from the defaults.
- **const member functions**: `double Cat::get_weight_grams() const { return weight_grams; }` — "I promise this function's code will NOT change this object's member variables"; compiler catches violations; always use with getters.
- Organizing code: header (.hpp) holds declarations (tell the compiler the code exists somewhere and can be called in this compilation unit); source (.cpp) holds definitions.

## Deck 2: destructor
- Standard member functions so far: default constructor, copy constructor; next: the destructor.
- Member function automatically called before the object is destroyed; write code to delete dynamic memory of member pointers; purpose: free resources the object acquired during its lifetime; invoked when the lifetime ends: program termination (statics), end of scope, explicit `delete` / `delete[]`.
- Complementary operation of the default constructor, notation `~`: `~Complex() { cout << "Destroyed!" << endl; }`.
- Rules (return to them later): 1. **never throw exceptions from a destructor**; 2. **if a class contains a virtual function, the destructor should be virtual too**.
- `~MyVector() { delete[] data; }` with `unsigned vector_size; double * data; //will point at dynamic memory`.

## Deck 2: forward declaration
- Conundrum: Car has Wheels; a Wheel has a pointer to the Car that possesses it. Car.hpp `#include "Wheel.hpp"`, Wheel.hpp `#include "Car.hpp" // UH OH! THIS IS TROUBLE!` → Car.hpp includes Wheel.hpp which includes Car.hpp which includes Wheel.hpp…; "the compiler error message is not helpful".

- Caution: with a forward declaration you can only declare a **reference or a pointer** to that type (the compiler does not know how to allocate the object); forgetting gives `field 'class' has incomplete type`.

## Deck 2: inheritance
- C++ implements inheritance, polymorphism, abstract classes and interfaces; C++ terms: base class, derived class. Java `class Circle extends Shape` ↔ C++ `class Circle : public Shape { … }`.
- Push common attributes as high as possible; derived classes inherit all the **accessible** members of the base; `public` may be replaced by `private` or `protected` in the derived class header, which limits the most accessible level of the inherited members.
- Access table: members of the same class: public yes, protected yes, private yes; members of a derived class: yes, yes, **no**; not members: yes, no, no.
- Spy: `publicPrint()` public, `protectedPrint()` protected, `privatePrint()` private. `class PublicSpy : public Spy` → public/protected/private stay; `class ProtectedSpy : protected Spy` → publicPrint becomes protected; `class PrivateSpy : private Spy` → publicPrint and protectedPrint become private; `class PrivateSpy2 : private PrivateSpy` → nothing accessible. Shipped Visibility/Spy.hpp comment: "classes inherit privately by default" (`class PrivateSpy : Spy`); each `print()` calls `publicPrint(); protectedPrint(); //privatePrint();` (private never accessible); PrivateSpy2::print has all three commented out. main: `PrivateSpy p; p.print();` → `public`, `protected`.
- What is inherited: a publicly derived class inherits access to everything **except** 1. constructors*, 2. destructor*, 3. friends, 4. private members. *not inherited as such but automatically called by the derived class's constructors and destructor.
- Which base constructor gets called: specify in the derived constructor's member initialization list (the "call to super" looks like member initialization); pass parameters to the base constructor; otherwise the default constructor is called (just like Java). Examples whichconstructor.cpp and private.cpp.
- whichconstructor.cpp: `Base()` prints `Base: no parameters`, `Base(int a)` prints `Base: int parameter`; `Derived_One(int a) // LOOK AT THIS!` (no initializer) prints `Derived_One: int parameter\n`; `Derived_Two(int a) : Base(a) // COMPARE TO THIS!`. main `Derived_One first_child(0); Derived_Two second_child(0);` → `Base: no parameters` / `Derived_One: int parameter` / blank / `Base: int parameter` / `Derived_Two: int parameter` / blank.
- private.cpp: `class A { private: int x; public: A() : x{0} { cout << "A()" << endl; } A(int x) : x{x} { cout << "A(" << x << ")" << endl; } int get_x() const; void set_x(int); };` `class B : public A { B(): A() { cout << "B()" << endl; } B(int x) { cout << "B(" << get_x() << ")" << endl; } }` — the shipped `B(int x)` ignores x, so `B c{2}` would print `A()` then `B(0)`. Commented alternatives: `B(int x) : A{x}` (correct: `A(2)`, `B(2)`); `// NO DON'T DO THIS  B(int x) { set_x(x); ... }` (default-constructs A then assigns); `B(int x) : x{x}` → `error: member initializer 'x' does not name a non-static data member or base class` (x is private in A, and a derived class cannot initialize a base's member in its list anyway). main runs only `A a;` → `A()`.

## Deck 2: polymorphism and virtual functions
- pol·y·mor·phism: Greek poly (many) + morphe (form); "a feature of a programming language that allows routines to use variables of different types at different times".
- "It's EASY! A pointer to a derived class is type-compatible with a pointer to its base class." (Java: everything is a pointer.)
- polymorphism.cpp: `class Shape { private: int counter; protected: int width, height; public: void set_values(int a, int b) { width = a; height = b; } }; class Rectangle: public Shape { public: int area() { return width * height; } }; class Triangle: public Shape { public: int area() { return width * height / 2; } };` main: `Rectangle rect; Triangle trgl; Shape * shape1 = &rect; Shape * shape2 = &trgl; shape1->set_values(4,5); shape2->set_values(4,5); //cout << shape1->counter; // WILL THIS WORK? (no: private)  cout << "Rectangle area: " << rect.area(); cout << "Triangle area: " << trgl.area();` → `Rectangle area: 20`, `Triangle area: 10`. `shape1->area()` would not compile: no area in Shape.
- "But that area member function… there was no area member function in Shape; could not use a Shape pointer to ask a Rectangle or Triangle for the area. Q: how can we overcome this? A: virtual members!"
- Virtual member function: a base class member function that can be redefined (Java: overridden) in the derived class; add the `virtual` keyword to the declaration; **non-virtual members of the derived class cannot be accessed through a reference of the base class**. Permits a member of the derived class with the same name as the base member to be appropriately called from a pointer; a class that declares or inherits a virtual function is a **polymorphic class**; permits **dynamic binding aka late binding aka polymorphic method dispatch**.
- virtual.cpp: `class Polygon { protected: int width, height; public: void set_values(int a, int b); virtual int area () { return 0; } // THIS IS A BAD EXAMPLE, BUT OK UNTIL LATER THIS WEEK }; Rectangle::area → width*height; Triangle::area → (width*height/2)`. main: `Polygon* poly = &rect; poly->set_values(4,5); cout << "Rectangle area: " << poly->area(); poly = &trgl; poly->set_values(4,5); cout << "Triangle area: " << poly->area();` → 20, 10. Comment: "polymorphism only works with pointers or references"; "polymorphism fails without pointers or references": `// Polygon poly2 = rect; poly2.set_values(4,5); cout << poly2.area(); // would print 0` (object slicing).
- More: `virtual` specifies that a non-static member function supports dynamic binding; used with pointers and references; a call to an overridden virtual function invokes the derived behaviour; invoke the original with the base name and the scope operator (qualified name lookup): `var.Base::function();`.
- virtual2.cpp: `Base::print()` virtual prints `base`; `Derived::print() override` prints `derived`. `Base b; Derived d; Base& br = b; Base& dr = d; br.print(); dr.print();` → base, derived; `Base* bp = &b; Base* dp = &d; bp->print(); dp->print();` → base, derived; `br.Base::print(); dr.Base::print();` → base, base; `Base baseDerived = d; //d is a derived type  baseDerived.print(); //prints what?` → **base** (copying into a Base object slices off the Derived part). Full output: base / derived / (blank) / base / derived / (blank) / base / base / (blank) / base.

## Testing2.pptx: Testing and debugging (40 slides)
- Warm-up "What's the output?": Java `int sum = 1; for (int i = 0; i <= 4; i++); { sum = sum + 1; } println("The result is: " + sum); println("Double result: " + sum + sum);` → the `;` after the for makes the body empty, the block runs once: `The result is: 2` and `Double result: 22` (string concatenation).
- Errors: early errors are syntax errors (IDE spots them); later errors are logic errors = BUGS (IDE cannot help; some have no obvious manifestation). Typical: implementing a class/method incorrectly, failing to meet the specification, inappropriate object request (invalid index), inconsistent object state (arising through class extension). Not always programmer error: environment (incorrect URL, network interruption), file processing (missing files, permissions) "but it usually is".
- Prevention vs detection: lessen likelihood with software engineering techniques like encapsulation; improve detection with modularization and documentation; test and debug.
- **Testing != Debugging**: testing reveals the EXISTENCE of a problem; debugging pinpoints the SOURCE; the manifestation may occur some distance from its source.
- Debugging review: print statements (most popular; correct places; output may be voluminous; turning on/off needs forethought); walkthroughs (tabulate key variables, document state changes after each call; verbal walkthrough to a peer; formal inspections exist); debuggers (language- and environment-specific; breakpoints; Step / Step-into; call stack; watch variables and object state). In-class activity: sum a range of integers, breakpoint, watch the aggregator.
- Testing = Verification + Validation: verification "Did we build the app correctly?" (find incorrect/undesirable behaviour); validation "Did we build the correct app?" (demonstrate to developer and customer that it meets requirements).
- Testing axioms: testing can't show that bugs don't exist; a bug is a bug only if it's observed (unfound bugs are undiscovered bugs); we cannot fix all bugs; virtually impossible to find subtle bugs while major bugs remain; specifications are a moving target.
- Fundamentals: format and organize code, document, good names/constants; CLion analysis tools (lightbulb quick-fixes, right-margin analysis, wiggly underlines). Dynamic testing: provide input, receive output, compare with expected. Static testing: reviewing source code, documentation, project plan. Understand the contract and look for violations; positive tests (valid data) and negative tests (invalid data). Test boundaries: zero, one, full; max/min; just inside/just outside; typical values; error values. Create DISJOINTED EQUIVALENCE PARTITIONS: coverage (inputs processed the same way), disjointedness (each group is a partition), representation (each test exercises one and only one partition); "like the Cartesian product".
- Example: a function that processes numbers 100 to 999: partitions <100, 100–999, >999; choose 5 tests: 50 (way off), 100 and 999 (boundaries), 500 (inside), 1500 (way off).
- Tactics: functional (black box: from specifications, system atomic, covers specified behaviour) vs structural (white box: from code, examines internals, covers implemented behaviour).
- Kinds used in COMP 3522: assertions, unit tests, regression testing.
- Assertions document and check preconditions (what the user must promise), postconditions (what the code promises if preconditions hold), invariants (what never changes). `assert` macro from `<cassert>` (inherited from C) evaluates an expression and immediately terminates the program if false; turn off with `#define NDEBUG` before `#include <cassert>`. Example `double square_root(double x) { check_somehow(x >= 0); … assert(result >= 0.0); return result; }`.
- Unit tests: WHAT a piece of code exercising a very small specific area of functionality; HOW invokes a function in a particular context; EXAMPLE add a large value to a sorted list and confirm it appears at the end; GOAL isolate important parts and show they are free of certain faults early. A unit is the smallest testable part (function, method, behaviour, composite components with defined interfaces). Each unit test: **Assemble, Act, Assert**; consider starting state, inputs, expected results/end state. JUnit review: test methods, test cases (classes), assertions, fixtures. C++: lots of frameworks; we learn **Catch**.
- Test automation: thorough testing is repetitive; frameworks automate; regression testing = re-running tests; build a test suite. Regression: whenever you find and fix a bug, add a test for it and rerun all tests (fixing new bugs can reintroduce old ones); run as frequently as possible.
- Strategy TDD: write tests first, implement, code is complete when tests pass, refactor and pass again; "hundreds or thousands of unit tests before writing a single line of code".
- Strategy Simplify: find the simplest test input that provokes the bug (often not the one that revealed it); start with the revealing data and keep narrowing ("binary search, anyone?"); modularity: start with everything and take pieces away until the bug disappears, or start with nothing and add until it appears; modular reasoning: trace and view intermediate results; binary search over the ordered set of statements.
- Remember: errors are a fact of life; good techniques reduce them; employ a range of approaches; make testing a habit; automate; continually repeat tests.

## UMLDiagramsReview.pdf
- UML: modelling language of diagrams used to specify, visualize, construct, document; class, collaboration, sequence diagrams.
- Class diagram: static structure; classes with attributes and operations; relationships; language agnostic. Rectangle: top = class name, middle = attributes and types, bottom = methods.
- Relationships: **Association** — reference-based, A contains member variables of B (plain line/arrow). **Generalization/Inheritance** — A is a subclass of B (hollow triangle arrow). **Realization/Implementation** — A implements interface B (dashed line, hollow triangle). **Dependency** — communication where one class does not necessarily contain an instance of the other; A contains methods that use B (dashed arrow). **Composition** — a class is made up of and has references to objects of another; parts cannot exist without the whole (filled diamond): order 0..1 — 1..* order_items; if an order is destroyed so are its order_items. **Aggregation** — a class references an object of another; the referenced class lives on if the referencing class is destroyed (hollow diamond): pond 0..1 — 0..* ducks.
- Examples: Car composed of carburetors, exactly 1 carburetor, carburetor belongs to 0..1 cars. Car with strings model, manufacturer and methods turnRight, turnLeft, driveStraight; Car has a dependency on Wheel (some method uses Wheel as a local variable or parameter). Professor aggregates 1..* Classes (list `listOfStudents`); each Class has exactly 1 Professor (list `Students`). Person (string name, int age); Student subclass (list grades); Professor subclass (list listOfStudents).
- Collaboration (communication) diagram: interactions as a sequence of messages from a structural perspective; a use case or subset. Notations: object = square with `object name : class name` underlined; actor = invoker, named, has a role; links = solid lines between objects/actors, instances of associations, messages travel across them; messages = labelled arrows near a link, sender to receiver, numbered for sequence, same-call messages get decimals 1.1, 1.2.
- Sequence diagram: interactions as a sequence of messages from a **time-based** perspective including the lifetime of interactions. Actor (external to the subject: human users, external hardware, other subjects); lifeline (one participant; name and class in the top box; dotted line = place in sequence); activations (thin rectangle on the lifeline = duration of an operation). Messages: call message (invoke an operation on the target lifeline), return message (information back to the caller, a return statement), self message (invoke on the same lifeline), create message (instantiation of the target lifeline).
